# ADR 0010 — Evals: experiments as data, graders as pluggable async protocols, four-axis matrix

**Status:** Accepted
**Date:** Initial scaffolding for `strata_forge.evals`
**Supersedes:** —
**Superseded by:** —

## Context

`strata_forge.evals` is the experiment runner: it takes a definition of
"these models, these prompts, this dataset, these graders" and
produces typed results that downstream tools (CI eval gate, reports,
trace replay) consume.

Three design questions had to be answered before any code lands:

1. **What shape is an experiment?** A function call? A class? A
   declarative data object?
2. **What is a grader?** A callable? A class? A Protocol? Does it
   need state?
3. **What does the result look like?** Per-trial outputs? Aggregated
   metrics? Both?

Picking wrong here means the CI gate and reports either reach around
the runner for shapes they need or import provider SDKs to recompute
things — both defeat the layered design.

## Decision

### Experiments are declarative Pydantic data

```python
class Experiment(BaseModel):
    name: str
    models: tuple[str, ...]              # logical model names
    prompts: tuple[str, ...] = ()        # prompt-registry names; empty = raw message lists
    dataset_name: str
    dataset_version: str | None = None   # None = latest
    grader_names: tuple[str, ...]
    sampling: SamplingParams
    metadata: dict[str, Any] = {}
```

An `Experiment` is **pure data**, frozen Pydantic, with content-hash
identity. Two callers describing "the same experiment" produce the
same bytes, the same hash, and the same cache key — which makes
"have we already run this experiment?" a one-line dict lookup
against the result store.

The runner consumes the `Experiment` and resolves
names against the live registries (`strata_forge.llm`, `strata_forge.prompts`,
`strata_forge.datasets`). No `Experiment` instance holds an `LLMClient` or
a `Dataset` directly — those resolve at run time, so a serialized
Experiment is portable across processes.

### Graders are async Protocols, not classes

```python
@runtime_checkable
class Grader(Protocol):
    @property
    def name(self) -> str: ...

    async def grade(
        self,
        *,
        item: DatasetItem,
        response: LLMResponse,
    ) -> GraderResult: ...
```

The Protocol is async because LLM-judge graders need
`LLMClient.complete_structured`, and the rest of `strata_forge.*` is
async-only. Pure-text graders (`ExactMatch`, `Regex`) just don't
await anything; their `grade` is `async def` for shape uniformity.

Graders are NOT required to subclass anything. Any object with the
right shape works — `runtime_checkable` lets the runner accept user
code that wasn't written with `forge` in mind. The shipped graders
are simple classes (`ExactMatch(case_sensitive=True)`) because
config-via-constructor reads better than config-via-closure, but
that's a convention, not a requirement.

### Trials and Outcomes are typed Pydantic shapes

A **Trial** is one row in the experiment matrix — one
`(model, prompt, item)` combination plus the LLM response that
came back:

```python
class Trial(BaseModel):
    experiment_name: str
    model: str
    provider: str
    prompt_name: str | None      # None when raw messages were used
    item_id: str
    response_text: str
    usage: Usage
    cost_usd: float
    cache_hit: bool
    latency_ms: float
```

A **GraderResult** is one grader's verdict on one Trial:

```python
class GraderResult(BaseModel):
    grader_name: str
    score: float                 # typically in [0, 1]
    passed: bool
    explanation: str = ""
    metadata: dict[str, Any] = {}
```

An **Outcome** binds them together:

```python
class Outcome(BaseModel):
    trial: Trial
    grader_results: tuple[GraderResult, ...]
```

`tuple[GraderResult, ...]` mirrors the choice in `strata_forge.datasets`:
Pydantic's `frozen=True` only prevents attribute reassignment, so
collections that should be structurally immutable use tuples, not
lists.

### Four-axis matrix

The experiment matrix has four axes:

```
models × prompts × items × graders
```

Trials are generated by the cross-product of `models × prompts × items`.
Each Trial is then graded by every `Grader` in `grader_names`. The
runner is free to parallelize across the first three axes; graders
run sequentially within a Trial because some compose (e.g., LLM-judge
might need a previous grader's output).

### Result-store contract

The runner produces `tuple[Outcome, ...]`. Aggregation (accuracy,
F1, BLEU, …) and reports (Markdown, HTML, CI gate) consume that
tuple. The runner does not own metric computation or report
generation — those are separate, composable layers downstream.

## Consequences

**Positive**

- **Reproducibility.** An `Experiment` is serializable; the same
  bytes always describe the same run. Combined with the
  content-hash dataset versioning from ADR 0009, "did we already
  evaluate this combination?" is decidable without re-running.
- **No vendor lock-in.** Graders are a Protocol — users can ship
  custom graders without inheriting from anything in `forge`. CI
  pipelines can drop in proprietary graders without forking the
  module.
- **Async-uniformity.** Every grader is `async`, so the runner can
  freely schedule them via `asyncio.gather` without dispatching on
  "is this grader sync or async?".
- **Type-checked end to end.** `Experiment → Trial → Outcome` are
  all Pydantic v2 with `extra="forbid"`. The wire shape is stable;
  pyright catches mismatches between the runner and downstream
  consumers.

**Negative**

- **Protocol vs ABC trade-off.** A Protocol means we can't enforce
  invariants in a base class (like "score must be in [0, 1]"). We
  enforce them on `GraderResult` instead, via Pydantic field
  constraints — which catches the same bugs at a slightly later
  point.
- **Name resolution.** Experiments carry *names* (model name,
  prompt name, grader name) rather than concrete objects. The
  runner needs registries to resolve them. That's intentional for
  portability but adds a level of indirection.

**Mitigations**

- The runner gets explicit `Grader` instances passed in (or
  resolved by name from a `GraderRegistry`, should a grader that
  needs one arrive). Users wiring their own pipelines can bypass
  the registry entirely.
- We document the "experiment is data, runner is behavior"
  separation in the module README so the indirection isn't
  surprising.

## Alternatives considered

1. **Experiment as an executable class with `run()` method.**
   Convenient for one-off scripts but hard to serialize, hard to
   diff, hard to cache. Rejected — declarative data + a separate
   runner is the more composable shape.

2. **Graders as plain callables.** Simpler signature, but loses
   `.name` (used in reports) and makes config awkward
   (closures vs. classes). Rejected — the cost of writing
   `class ExactMatch:` is trivial.

3. **Synchronous Grader protocol with sync wrappers for LLM-judge.**
   Cleanly mirrors the bulk of graders (pure text). Rejected
   because every other public function in `strata_forge.*` is async; a
   sync grader Protocol would be the one exception, and an
   `asyncio.run`-inside-grader pattern would block the runner's
   event loop.

4. **Single `Outcome` per `(Trial, Grader)` pair (flat list).**
   Closer to a SQL row layout but loses the natural per-Trial
   grouping that reports need. Rejected — the
   `Outcome { trial, grader_results: tuple[...] }` shape is what
   reports actually iterate over.
